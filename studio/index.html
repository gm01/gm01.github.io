문제 01 / 인증

“성공 응답”도 다시 확인

HTTP 200이어도 본문에는 인증 만료가 담길 수 있었습니다. 응답 내용을 확인해 준비 단계 실패와 앱 기능 실패를 구분했습니다.

문제 02 / 화면

기다림 대신, 탐색과 상태 확인

목록 밖 주문은 스크롤하며 다시 찾고, 화면 전환을 확인한 뒤 다음 동작을 수행하도록 개선했습니다.

문제 03 / 재현

실패를 설명할 수 있는 기록

실행 리포트와 실패 화면·화면 구조 정보를 수집해 인증, 데이터, 앱 중 어느 단계에서 실패했는지 확인했습니다.

Python · pytest · Appium · Requests · Page Object

설계 판단과 실행 기록 자세히 보기 ↗

구현 범위 퀵·대리 정상 흐름의 자동화 기반입니다. 실패·취소 전체 시나리오와 정기 CI 실행까지 완료한 것으로 표현하지 않습니다.

02 / HOW I WORK

도구를 쓰는 것보다,
판단을 남기는 일.

Define. Build. Verify.나의 QA 엔지니어링 방식
01

요구사항을 검증 기준으로 바꿉니다.

기획 Q&A로 조건과 예외를 확인하고, 변경 사항을 테스트케이스·회귀 범위에 반영합니다. 리소스와 진행 현황까지 함께 관리합니다.

02

AI와 구현하되, 결과는 직접 검증합니다.

시나리오와 기대 상태를 정의하고 AI 에이전트로 구현·수정안을 작성합니다. 실제 API 응답과 앱 실행 결과를 비교하며 실패 조건을 보정합니다.

03

다음 실행에서도 쓸 수 있게 만듭니다.

API, 화면 동작, 시나리오를 분리하고 인증·테스트 데이터 준비를 재사용합니다. 실패 단계와 증적을 남겨 후속 분석을 돕습니다.
